# Chrome Web Store Privacy Disclosure Draft

This document is a publisher-ready drafting aid for VaultKey Browser 1.0.0. The publisher must compare it with the current Developer Dashboard questions and the final submitted build. It is not a claim that a listing or public privacy URL already exists.

## Single purpose

VaultKey Browser is a local-first password manager that lets users securely store, generate, organize, and explicitly fill credentials in their browser.

## Data handled

- **Authentication information:** usernames/email addresses and passwords entered or generated by the user.
- **User-generated content:** credential notes and labels entered by the user.
- **Website information and browsing activity:** saved website addresses/hostnames and the active tab URL used only for current-site suggestions and explicit Quick Fill.
- **Website content/form data:** visible login input fields accessed only during a user-initiated Quick Fill operation; page content is not collected or retained as a dataset.
- **Extension settings:** Auto Lock, clipboard protection, and generator preferences.

All of this data is processed locally. Username/email, password, and notes are encrypted before persistent storage. Service name, saved website/hostname, favorites, and timestamps remain local plaintext metadata needed for vault organization and site matching. Password-protected backups encrypt the complete persistent payload, including metadata.

## Collection and transmission answers

- Data is not transmitted to the developer or a third party.
- Data is not sold.
- Data is not used or transferred for advertising.
- Data is not used or transferred for creditworthiness or lending.
- Data is not used for analytics, telemetry, profiling, or unrelated purposes.
- VaultKey has no backend, account system, cloud sync, runtime network request, or remote code.
- User data is handled only to provide the extension's single user-facing purpose.
- Users can delete individual entries or reset all VaultKey-owned local data.

Local-only handling still needs disclosure in the Chrome Web Store. Authentication information and saved/active website information should be declared accurately in the Dashboard rather than marked as “not collected” merely because they remain on-device.

## Permission justifications

- `storage`: encrypted vault, local metadata/settings, and temporary trusted session state.
- `activeTab`: active URL and temporary access only after the user invokes VaultKey.
- `scripting`: one-time main-frame Quick Fill after explicit account selection.
- `alarms`: Auto Lock and optional clipboard-expiry scheduling.
- `offscreen`: minimal clipboard comparison/clear document required by service-worker constraints.
- Optional `clipboardRead`/`clipboardWrite`: requested only when the user enables clear-if-unchanged clipboard protection.

See `docs/PERMISSIONS.md` for the complete rationale.

## Privacy policy URL

**Publisher action required:** publish `PRIVACY.md` at a stable, public HTTPS URL controlled by the publisher and paste that exact URL into the Chrome Web Store Developer Dashboard. Do not submit a repository-relative path, localhost URL, temporary preview URL, or invented domain.

## Prominent user-facing disclosures

The product UI describes local storage, Quick Fill's explicit action, lack of automatic submit, optional clipboard access, destructive reset, and backup behavior. The publisher should confirm these disclosures remain accurate in the submitted build and listing.

## Certification check

Before submission, compare every Dashboard checkbox with the final ZIP, current Chrome Web Store User Data Policy, `PRIVACY.md`, and the store description. If behavior or permissions change, update all four together.
